Step 1: Set project, region, and zone dynamically
PROJECT_ID="$(gcloud config get-value project 2>/dev/null)"

[ -n "$PROJECT_ID" ] && [ "$PROJECT_ID" != "(unset)" ] || \
PROJECT_ID="$(gcloud projects list --filter='lifecycleState=ACTIVE' --format='value(projectId)' --limit=1)"

gcloud config set project "$PROJECT_ID"

REGION="asia-south1"

ZONE="$(gcloud compute zones list \
  --filter="name~'^${REGION}-[a-z]$' AND status=UP" \
  --format='value(name)' \
  --limit=1)"

gcloud config set compute/region "$REGION"
gcloud config set compute/zone "$ZONE"

echo "PROJECT_ID=$PROJECT_ID"
echo "REGION=$REGION"
echo "ZONE=$ZONE"
Explanation

gcloud config get-value project checks which project is currently selected in Cloud Shell.

The second command checks whether the project value is empty or unset. If it is unset, it automatically picks the first active project from your GCP account.

gcloud config set project "$PROJECT_ID" sets that project as the active project.

REGION="asia-south1" sets Mumbai region.

The ZONE="$(gcloud compute zones list ...)" command dynamically selects one available zone inside asia-south1, for example asia-south1-a.

gcloud config set compute/region and gcloud config set compute/zone save your default region and zone so you do not need to type them manually again.

Step 2: Enable required APIs
gcloud services enable compute.googleapis.com iap.googleapis.com
Explanation

compute.googleapis.com is required for Compute Engine VMs, disks, firewall rules, and networking.

iap.googleapis.com is enabled because we will use IAP-based SSH tunneling. IAP TCP forwarding allows encrypted SSH/RDP/other TCP tunnels to VM instances and is useful when you do not want direct public access.

Step 3: Check default VPC and recreate only if missing
gcloud compute networks describe default >/dev/null 2>&1 || \
gcloud compute networks create default --subnet-mode=auto
Explanation

This checks whether the default VPC exists.

If it exists, nothing is created.

If it does not exist, the command creates the default VPC in auto subnet mode.

We are using the default VPC because you asked not to create a custom VPC for now.

Step 4: Create firewall rules in default VPC
gcloud compute firewall-rules describe nagios-allow-iap-ssh >/dev/null 2>&1 || \
gcloud compute firewall-rules create nagios-allow-iap-ssh \
  --network=default \
  --direction=INGRESS \
  --action=ALLOW \
  --rules=tcp:22 \
  --source-ranges=35.235.240.0/20 \
  --target-tags=nagios-lab
Explanation

This creates a firewall rule for SSH access through IAP.

--network=default means the firewall rule is created inside the default VPC.

--direction=INGRESS means this rule controls incoming traffic.

--rules=tcp:22 allows SSH.

--source-ranges=35.235.240.0/20 allows SSH only from Google IAP TCP forwarding IP range. Google Cloud documents this range for IAP TCP forwarding.

--target-tags=nagios-lab means this SSH rule applies only to VMs having the nagios-lab network tag.

gcloud compute firewall-rules describe nagios-allow-nrpe-from-server >/dev/null 2>&1 || \
gcloud compute firewall-rules create nagios-allow-nrpe-from-server \
  --network=default \
  --direction=INGRESS \
  --action=ALLOW \
  --rules=tcp:5666 \
  --source-tags=nagios-server \
  --target-tags=nagios-client
Explanation

This allows NRPE traffic from Nagios server to client VMs.

tcp:5666 is the NRPE port.

--source-tags=nagios-server means only the VM tagged as nagios-server can initiate this traffic.

--target-tags=nagios-client means this rule applies only to client VMs.

So the flow becomes:

nagios-server -> tcp:5666 -> nagios-client-1 / nagios-client-2
gcloud compute firewall-rules describe nagios-allow-icmp-from-server >/dev/null 2>&1 || \
gcloud compute firewall-rules create nagios-allow-icmp-from-server \
  --network=default \
  --direction=INGRESS \
  --action=ALLOW \
  --rules=icmp \
  --source-tags=nagios-server \
  --target-tags=nagios-client
Explanation

This allows ping from Nagios server to client VMs.

Nagios can use ICMP ping checks to detect whether a host is up or down.

Google Cloud recommends using specific source ranges instead of broad ranges like 0.0.0.0/0 when creating firewall rules.

Step 6: Create Nagios server VM
gcloud compute instances describe nagios-server --zone="$ZONE" >/dev/null 2>&1 || \
gcloud compute instances create nagios-server \
  --zone="$ZONE" \
  --machine-type="$MACHINE_TYPE" \
  --network=default \
  --tags=nagios-lab,nagios-server \
  --image-family="$IMAGE_FAMILY" \
  --image-project="$IMAGE_PROJECT" \
  --boot-disk-size=10GB \
  --boot-disk-type=pd-standard \
  --boot-disk-auto-delete \
  --provisioning-model=STANDARD
Explanation

This creates the Nagios monitoring server.

gcloud compute instances describe ... || gcloud compute instances create ... prevents error if the VM already exists.

--machine-type="$MACHINE_TYPE" uses e2-micro.

--network=default places the VM in the default VPC.

--tags=nagios-lab,nagios-server attaches network tags used by firewall rules.

--boot-disk-size=10GB creates a small boot disk.

--boot-disk-type=pd-standard uses standard persistent disk.

--boot-disk-auto-delete deletes the boot disk when the VM is deleted.

--provisioning-model=STANDARD explicitly creates a standard VM, not Spot.

Step 9: Install Nagios Core on Nagios server
gcloud compute ssh nagios-server \
  --zone="$ZONE" \
  --tunnel-through-iap \
  --command="echo 'postfix postfix/main_mailer_type select No configuration' | sudo debconf-set-selections && sudo apt-get update && sudo DEBIAN_FRONTEND=noninteractive apt-get install -y apache2 apache2-utils nagios4 nagios-nrpe-plugin monitoring-plugins nagios-plugins-contrib"
Explanation

This command connects to nagios-server and installs Nagios.

gcloud compute ssh nagios-server connects to the Nagios VM.

--tunnel-through-iap forces SSH through IAP.

debconf-set-selections preselects “No configuration” for Postfix so the installation does not stop and ask questions.

apt-get update refreshes Ubuntu package metadata.

apache2 installs Apache web server for the Nagios web UI.

apache2-utils gives tools like htdigest.

nagios4 installs Nagios Core 4.

nagios-nrpe-plugin installs the plugin used by the Nagios server to check remote NRPE clients.

monitoring-plugins and nagios-plugins-contrib install common monitoring plugins.

Ubuntu’s Nagios Core 4 guide installs nagios4 and nagios-nrpe-plugin for the monitoring server.

Step 14: Allow Nagios server IP in NRPE config
for VM in nagios-client-1 nagios-client-2; do
  gcloud compute ssh "$VM" \
    --zone="$ZONE" \
    --tunnel-through-iap \
    --command="sudo sed -i 's/^allowed_hosts=.*/allowed_hosts=127.0.0.1,::1,$NAGIOS_IP/' /etc/nagios/nrpe.cfg"
done
Explanation

This modifies:

/etc/nagios/nrpe.cfg

It updates the allowed_hosts line.

After this change, NRPE will allow requests only from:

127.0.0.1
::1
Nagios server private IP

This is important because you do not want every machine to execute NRPE checks on your clients.

Step 15: Create NRPE check commands file locally in Cloud Shell
cat > gcp-lab-nrpe.cfg <<'EOF'
command[check_root_disk]=/usr/lib/nagios/plugins/check_disk -w 20% -c 10% -p /
command[check_load_custom]=/usr/lib/nagios/plugins/check_load -r -w 2.0,1.5,1.0 -c 4.0,3.0,2.0
command[check_users_custom]=/usr/lib/nagios/plugins/check_users -w 5 -c 10
command[check_total_procs_custom]=/usr/lib/nagios/plugins/check_procs -w 150 -c 200
command[check_zombie_procs_custom]=/usr/lib/nagios/plugins/check_procs -w 5 -c 10 -s Z
EOF
Explanation

This creates a small NRPE config file in Cloud Shell.

It defines five checks:

Root disk usage
CPU load
Logged-in users
Total processes
Zombie processes

check_root_disk warns when free disk space is below 20% and becomes critical below 10%.

check_load_custom checks CPU load average.

check_users_custom warns at 5 logged-in users and critical at 10.

check_total_procs_custom warns at 150 processes and critical at 200.

check_zombie_procs_custom checks zombie processes.

Step 16: Copy NRPE config to both clients and restart NRPE
for VM in nagios-client-1 nagios-client-2; do
  gcloud compute scp gcp-lab-nrpe.cfg "$VM":/tmp/gcp-lab-nrpe.cfg \
    --zone="$ZONE" \
    --tunnel-through-iap

  gcloud compute ssh "$VM" \
    --zone="$ZONE" \
    --tunnel-through-iap \
    --command="sudo mv /tmp/gcp-lab-nrpe.cfg /etc/nagios/nrpe.d/gcp-lab.cfg && sudo chown root:root /etc/nagios/nrpe.d/gcp-lab.cfg && sudo systemctl enable nagios-nrpe-server && sudo systemctl restart nagios-nrpe-server && sudo systemctl status nagios-nrpe-server --no-pager"
done
Explanation

gcloud compute scp copies the config file from Cloud Shell to each client VM.

The file is first copied to /tmp because direct copy to /etc/nagios/... needs sudo permission.

sudo mv moves the file into the NRPE config directory.

sudo chown root:root makes root the owner of the config file.

systemctl enable nagios-nrpe-server enables NRPE after reboot.

systemctl restart nagios-nrpe-server applies the new config.

systemctl status verifies NRPE is running.

Expected status:

active (running)
Step 17: Create Nagios NRPE command config locally
cat > gcp-nrpe-command.cfg <<'EOF'
define command {
    command_name    check_nrpe_custom
    command_line    /usr/lib/nagios/plugins/check_nrpe -H $HOSTADDRESS$ -c $ARG1$
}
EOF
Explanation

This defines a Nagios command named:

check_nrpe_custom

Nagios will use this command to call NRPE checks on remote clients.

$HOSTADDRESS$ is replaced by the client VM private IP.

$ARG1$ is replaced by the check name, for example:

check_root_disk
Step 18: Create Nagios clients config locally
cat > gcp-clients.cfg <<EOF
define host {
    use                     generic-host
    host_name               nagios-client-1
    alias                   GCP Nagios Client 1
    address                 $CLIENT1_IP
}

define host {
    use                     generic-host
    host_name               nagios-client-2
    alias                   GCP Nagios Client 2
    address                 $CLIENT2_IP
}

define service {
    use                     generic-service
    host_name               nagios-client-1,nagios-client-2
    service_description     PING
    check_command           check-host-alive
}

define service {
    use                     generic-service
    host_name               nagios-client-1,nagios-client-2
    service_description     Root Disk
    check_command           check_nrpe_custom!check_root_disk
}

define service {
    use                     generic-service
    host_name               nagios-client-1,nagios-client-2
    service_description     CPU Load
    check_command           check_nrpe_custom!check_load_custom
}

define service {
    use                     generic-service
    host_name               nagios-client-1,nagios-client-2
    service_description     Logged In Users
    check_command           check_nrpe_custom!check_users_custom
}

define service {
    use                     generic-service
    host_name               nagios-client-1,nagios-client-2
    service_description     Total Processes
    check_command           check_nrpe_custom!check_total_procs_custom
}

define service {
    use                     generic-service
    host_name               nagios-client-1,nagios-client-2
    service_description     Zombie Processes
    check_command           check_nrpe_custom!check_zombie_procs_custom
}
EOF
Explanation

This creates Nagios host and service definitions.

The first two blocks define the client hosts:

nagios-client-1
nagios-client-2

The address field uses the private IPs stored earlier.

The service blocks tell Nagios what to monitor.

For each client, Nagios will check:

PING
Root Disk
CPU Load
Logged In Users
Total Processes
Zombie Processes

/etc/nagios4/conf.d/
